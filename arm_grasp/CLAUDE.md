# CLAUDE.md

Guidance for Claude Code when working inside the `arm_grasp/` ROS package. Read this before making any change in this directory. End-user usage (build commands, run examples, service tables, parameter lists, troubleshooting) lives in `README.md`; this file focuses on what Claude must know to modify the package safely and to keep documentation aligned.

## Modification Policy

   * File layout under `scripts/`, `src/arm_grasp/`, `launch/`, `config/`, `models/`, `msg/`, or `srv/`.
   * ROS interface surface (service names, message and service fields, launch arguments, private parameter keys read by `arm_node_abs.py`).
   * The grasp pipeline contract inside `_plan_grasp_from_target` (NN IK -> voxel A* pre_path -> Cartesian pregrasp->grasp -> lift -> retract -> home), or any equivalent in `_plan_press_elevator_button`.
   * Per-arm pose compensation defaults (grasp: `~r_x_offset`, `~l_x_offset`, `~r_y_offset`, `~l_y_offset`, `~r_z_offset`, `~l_z_offset`; press: `~press_elevator_button_{r,l}_{x,y,z}_offset` — independent from the grasp pair because press fingertip and grasp palm drift differently; all three are subtracted from the target like the grasp offsets, and since +x is forward into the button a NEGATIVE x term over-presses (default `-0.005` = 0.5 cm forward)) or the lift / retract geometry (`~lift_dz`, `~retract_after_grasp`, `~retract_x_target`).

   * Joint conventions in `src/arm_grasp/joint_index.py` (`G1_23_JointArmIndex` indices, `ARM_DOF`, per-arm `ARM_JOINT_LIMITS`).
   * Low-level controller contract in `src/arm_grasp/arm_controller.py` (DDS topic names `rt/lowstate` / `rt/arm_sdk` / `rt/lowcmd`, motion-mode weight protocol incl. the `acquire_control` / `release_control` takeover and hand-back ramps, velocity clipping, control / subscribe thread split, the bundled-SDK path probe in `_ensure_local_unitree_sdk_path`).
   * NN IK assumptions in `solve_grasp_pose.py` and `elevator_button_ik.py` (5-input pose [x, y, z, rx_rad, rz_rad], per-arm `+/-0.17 y` rule for `rz`, fixed `rx = +/-pi/2` for the elevator-button arm).
   * Pinned-weight manifest (`config/model_weights.yaml`): the `hf_repo` / `hf_revision` / per-weight `sha256` fields, the per-entry `verify_sha256` opt-out flag (default true), the HF Hub repo identity (`g1-intellect/g1-arm-abs-models`), the nested-layout contract enforced by `scripts/fetch_weights.py` (preserves HF in-repo paths under `models/<filename>`; basenames repeat across `grasp_bottle/{left,right}/` and `elevator_button/{left,right}/`, so manifest lookup MUST key on the relative-to-models path).
   * Startup verifier contract in `src/arm_grasp/weight_verify.py`: the manifest-keyed sweep called from `arm_node_abs.__init__`, the per-entry `verify_sha256` opt-out branch, the `~force_full_weight_sha256` ROS param that overrides every opt-out. Missing manifest, missing weight, or sha256 drift triggers `rospy.logfatal` + `sys.exit(1)`.
   * Build configuration (service generation in `CMakeLists.txt`, the `catkin_install_python` script list, Python module list in `setup.py`, dependency list in `package.xml`).
2. `README.md` is the user-facing reference. When CLAUDE.md needs an update, check whether `README.md`, `launch/arm_node_abs.launch`, the `.srv` comment blocks, and the docstrings inside `scripts/arm_node_abs.py` and the modules under `src/arm_grasp/` need the same edit. Do not let them drift.
3. When intent or trade-off is ambiguous (whether to add a new service or fold a behaviour into an existing one, whether to relax a workspace clip, whether to expose a new tuning knob as a parameter or hardcode it, whether the per-arm pose-compensation default has shifted with new hardware, whether to change the voxel A* persistence policy, whether to make the elevator-button path share the grasp lift / retract leg), do not guess. ## Package Summary

`arm_grasp` is a ROS 1 (Noetic, Python 3.10) catkin package that owns absolute arm control for the Unitree G1. A single node, `g1_arm_simple` (`scripts/arm_node_abs.py`), wraps `ArmController` (DDS to the G1 via `rt/lowstate` / `rt/arm_sdk` / `rt/lowcmd`) and exposes a planning + execution surface for two end-effector tasks: bottle-style grasping and elevator-button pressing. Both tasks share the same backbone: a per-arm MLP IK predicts a 5-DOF arm configuration from a 5-D Cartesian pose, an obstacle-aware voxel A* planner produces a collision-free joint path from the current state to a pregrasp / pre-press pose using the live head-camera depth stream, and a Cartesian leg interpolates between pregrasp and grasp (or between pre-press and the button face). Hand services on each side are addressed through `/g1_hand_{left,right}/{pre_grasp, grasp_5f, release, point_gesture}` and the camera-side bottle lookup goes through `/perception/get_object_position` from `g1_camera`. The node never speaks to voice or perception topics directly; higher-level orchestrators (e.g. `main_process`) compose these services into full behaviours.

The voxel A* backend lives under `src/arm_grasp/voxel_planner_deploy/` and is wrapped by `src/arm_grasp/voxel_planner_adapter.py`. It memmaps two ~14 GB per-arm config bitmaps (decompressed once on disk after package install) plus three small sidecar arrays, samples the live `/camera/aligned_depth_to_color/image_raw` + `/camera/color/camera_info` topics, voxelizes the deprojected cloud into the planner's `torso_link` grid, and runs a 5D staged A* on a 4-deg/step joint grid with a deferred-yaw heuristic and optional 5D hyperrect shortcut compression.

* `scripts/arm_node_abs.py` is the only ROS-aware module. It owns parameter loading, NN IK invocation, voxel A* invocation, ROS service surface, controller wiring, and hand-service dispatch. Its method-level logic is extracted into decoupled `src/arm_grasp/` modules that take config / handles as explicit arguments. The node keeps `__init__`, `start`/`shutdown`, the `_handle_*` service callbacks (which build the ROS responses), and the per-pipeline `_*_ctx()` builders; the grasp plan/execute (`grasp_pipeline.plan_grasp` / `execute_grasp`), homing (`homing.go_home_dual` / `go_home_arm`), and the press planning core (`press_planning.plan_press_waypoints`) now live in their own modules and receive a context dataclass (`GraspContext` / `HomingContext` / `PressContext`) bundling the node's injected callables + config. The node's `_plan_grasp_from_target`, `_execute_grasp_pipeline`, `_go_home_impl`, `_go_home_arm_impl`, and the press handler's planning + execution sections are thin delegates (`press_planning.plan_press_waypoints` then `press_pipeline.execute_press`); the press handler keeps only request parse + `PressElevatorButtonResponse` mapping. Other node methods (`_compensate_pose`, `_solve_ai_ik`, `_check_joint_limits`, `_execute_waypoint_path`, `_call_trigger_service`, `_plan_astar_segments`, `_fire_release_background`, `_get_object_position`, `_init_voxel_planner`, …) are thin one-line delegates kept so internal call sites and signatures are unchanged. Parameter loading itself is centralised in `params.load_params` (still invoked from `__init__`, which applies the result via `self.__dict__.update` and keeps `~debug` / `~force_full_weight_sha256` inline); `_handle_plan_to_pose` delegates its planning to `pose_planning.plan_to_pose`. Helpers under `src/arm_grasp/` stay ROS-light: `arm_controller.py` and `voxel_planner_adapter.py` import `rospy` for their own life-cycle (controller initialisation, latched publishers, env probing) but do NOT advertise services; `hand_services.py`, `motion_exec.py`, `homing.py`, and `grasp_pipeline.py` touch `rospy` only for service waits / the 50 Hz poll loop / lift-call exception types and own no state (clients / controller / lift-call are injected). `joint_index.py`, `utils.py`, `solve_grasp_pose.py`, `elevator_button_ik.py`, `path_ops.py`, `joint_validation.py`, `pose_compensation.py`, `grasp_plan_math.py`, `astar_planning.py`, `press_planning.py`, and `nn_backend.py` (modulo the torch import) are fully ROS-free and must remain so for offline testing.
* `arm_controller.py` is the sole owner of the DDS channels and of the 250 Hz publish thread; service callbacks must talk to it through `ctrl_dual_arm`, `ctrl_left_arm`, `ctrl_right_arm`, `set_joint_angle`, or `go_home`, and must never write to `_msg.motor_cmd[*]` directly. The velocity clipping inside `_ctrl_motor_state` is what keeps the per-cycle joint delta inside `~velocity_limit * control_dt`, so any new motion entry point must route through `ctrl_*` rather than installing a fresh publish loop.
* `voxel_planner_adapter.py` is the only place that pairs the depth image with `CameraInfo` and deprojects it. The adapter caches per-arm `VoxelObstacleAStar` instances lazily (each is ~67 MB RSS), so warmup is opt-in via `~voxel_warmup_on_start`. The K-of-N persistence filter operates per arm because left and right planner grids have different origins; do not share the deque across arms.
* `solve_grasp_pose.compute_grasp_and_pregrasp` is the single source of truth for the per-arm `+/-0.17 y` offset rule and the `delta_rz_deg` open-vs-grasp wrist convention. The elevator-button path reuses the SAME `rz` rule via `elevator_button_ik.compute_rz_rad`; do not let the two diverge.
* The bottle-grasp MLP, the berry-pick MLP, and the elevator-button MLP are three separate file trees under `models/` (`grasp_bottle/`, `grasp_berry/`, `elevator_button/`). They share architecture (`MLPRegressor` 5->5 with default hidden dims `[256, 512, 256]`) but their weights and `x_scaler.pkl` are NOT interchangeable. The elevator-button models load lazily per arm in `elevator_button_ik._load_arm`. Both the bottle and berry grasp models load eagerly at node startup via `nn_backend.load_ai_tools` (`flag-based device`, Dropout-capable `MLPRegressor` — kept distinct from the probe-based, Dropout-free copy in `solve_grasp_pose.py`); the bottle pair goes through `_load_ai_tools` (`raise_on_missing=True` — a missing bottle weight is fatal) while the berry pair goes through `_load_berry_ai_tools` (`raise_on_missing=False` — a missing berry weight only warns at startup and is raised on the first `~pick_berry` call, so it cannot abort the bottle/press paths). The berry IK is reached through `_solve_ai_ik_berry` / `_solve_ai_ik_robust_berry` (same device as the bottle `_solve_ai_ik`, but its OWN `grasp_berry` weights AND its OWN pose compensation `_berry_pose_comp_cfg` built from `~pick_berry_{r,l}_{x,y,z}_offset` / `~pick_berry_tilt_deg` — default identity/zero; it does NOT reuse the bottle `~r_/~l_{x,y,z}_offset` or any press offset); `~pick_berry` injects it into the grasp pipeline by overriding BOTH `GraspContext.solve_ai_ik_robust` (pregrasp/grasp IK + A* goal joints) AND `GraspContext.build_horizontal_pre_to_target_waypoints` (the Cartesian pregrasp->grasp leg, via `_build_horizontal_pre_to_target_waypoints_berry`), and uses `_solve_ai_ik_robust_berry` directly in `_retract_berry`. Both overrides are required — the waypoint builder solves its own IK, so swapping only `solve_ai_ik_robust` would leave the Cartesian leg on the bottle model. Bottle grasp and press keep their own IK callables untouched.
* Hand services on each side are addressed via `_pre_grasp_client_for(arm)` / `_grasp_5f_client_for(arm)` / `_release_client_for(arm)` / `_point_gesture_client_for(arm)`. The `arm` field on every request routes through ONE string that selects the NN model + scaler, the voxel A* per-arm bitmap, the per-arm pose-compensation offsets (`~{r,l}_{x,y,z}_offset`), and the per-side hand client. Legacy single-bus params (`~pre_grasp_service_name`, `~grasp_5f_service_name`, `~release_service_name`) are still read and override BOTH sides when set; treat them as a back-compat fallback, not as the recommended path.

## ROS Interface

Node name: `g1_arm_simple` (set by the launch file and by `rospy.init_node`). All services live under `/g1_arm_simple/...`.

* Subscribed (through `VoxelPlannerAdapter`, only when `~use_astar_for_grasp` is true):
  * `~voxel_depth_topic` (default `/camera/aligned_depth_to_color/image_raw`, `sensor_msgs/Image`, `16UC1` mm or `32FC1` m).
  * `~voxel_camera_info_topic` (default `/camera/color/camera_info`, `sensor_msgs/CameraInfo`).
* Published:
  * `~voxel_obstacles` (default `/g1_arm_simple/voxel_obstacles`, `sensor_msgs/PointCloud2`, latched): voxel centers fed to A*, one cloud per `latest_voxel_obstacles` call (per plan or per live-publish tick).
  * `~voxel_obstacles_raw` (`/g1_arm_simple/voxel_obstacles_raw`, `sensor_msgs/PointCloud2`, latched): single-frame deprojected cloud before grid clipping. Useful when the voxel publisher is empty because the cloud does not intersect the planner grid.
* Services advertised (all relative to `~`):
  * `~move_arm_joints` (`arm_grasp/MoveArmJoints`): drive one arm to 5 joint angles.
  * `~infer_grasp_from_point` (`arm_grasp/InferGraspFromPoint`): NN-infer pregrasp + grasp joints from xyz. No motion.
  * `~plan_grasp_from_point` (`arm_grasp/PlanGraspFromPoint`): full grasp plan (NN + A* + Cartesian + lift + retract + home joint targets). No motion. Per-call `astar_override` tri-state matches `PlanGraspFromPointRequest`.
  * `~execute_grasp_from_point` (`arm_grasp/ExecuteGraspFromPoint`): full pipeline (plan + move + hand services + lift).
  * `~execute_astar_path_from_point` (`arm_grasp/ExecuteAstarPathFromPoint`): same as above with A* forced on.
  * `~plan_to_pose` (`arm_grasp/PlanToPose`): plan to an arbitrary 5-D Cartesian end-effector pose without grasp coupling. Optional `rx` / `rz` overrides (NaN means "derive from xyz using the NN convention").
  * `~GoHome` (`std_srvs/Trigger`): releases BOTH hands (best-effort, missing sides skipped) and runs a dual-arm A* home.
  * `~GoHomeArm` (`arm_grasp/GoHomeArm`): per-arm home with tri-state A* override (`ASTAR_USE_DEFAULT` / `ASTAR_FORCE_ON` / `ASTAR_FORCE_OFF`).
  * `~grasp_bottle` (`std_srvs/Trigger`): legacy path that pulls xyz from `/perception/get_object_position` using `~grasp_bottle_label` / `~grasp_bottle_index` / `~grasp_bottle_arm` and runs the grasp pipeline. Prefer the orchestrator-driven `plan_grasp_from_point` for new code.
  * `~pick_berry` (`std_srvs/Trigger`): pick ONE berry per call. Pulls all berries from `g1_camera/GetBerries` (`~berry_position_service_name`, default `/perception/get_berries`) filtered to `~pick_berry_ripeness` (default `black`), selects the nearest via `berry_lookup.nearest_berry`, picks the arm by the berry's torso_link y sign (`y > 0` -> left, else right), and runs the grasp pipeline via `_execute_berry_pick_pipeline`. That pipeline is `execute_grasp` with a `dataclasses.replace`-built `GraspContext` whose changes vs `_grasp_ctx()` are: swap the pre-grasp hand pose (`pre_grasp_service_for`/`_client_for`) to the berry approach service (`~pre_grasp_berry_service_name_{right,left}`, default `/g1_hand_{right,left}/pre_grasp_berry`), swap the post-grasp hand close (`grasp_5f_service_for`/`_client_for`) to the berry pinch service (`~grasp_berry_service_name_{right,left}`, default `/g1_hand_{right,left}/grasp_berry`), swap BOTH IK-bearing callables to the CLEAN berry IK (its own `grasp_berry` weights + its own `_berry_pose_comp_cfg`, NOT the bottle weights/offsets or any press offset) — `solve_ai_ik_robust` -> `_solve_ai_ik_robust_berry` (pregrasp/grasp joints + A* goal) and `build_horizontal_pre_to_target_waypoints` -> `_build_horizontal_pre_to_target_waypoints_berry` (the Cartesian pregrasp->grasp leg) — swap `compute_grasp_and_pregrasp` -> `_compute_grasp_and_pregrasp_berry` (xyz + rz from the shared geometry, but rx overridden on BOTH the grasp and pregrasp poses to `+pi/2` for the right arm / `-pi/2` for the left, vs the bottle's rx=0; positional accuracy comes only from `_berry_pose_comp_cfg` = `~pick_berry_{r,l}_{x,y,z}_offset` / `~pick_berry_tilt_deg`, default identity, so the detected berry position is used as-is) — set `grasp_hand_settle_time=~pick_berry_grasp_settle_sec` (default 0.7 s) so `execute_grasp` sleeps a fixed pause after commanding the grasp move and before triggering the berry grasp hand -- a simple settle instead of verifying the arm reached (the optional `require_grasp_reach` gate exists in `GraspContext` but is left off for berry, since the reach check was unreliable on repeated picks) -- and set `lift_after_grasp=False` + `retract_after_grasp=False` (no lift for berries). The handler passes `force_astar=~pick_berry_use_astar` (default TRUE), so by default the berry pick routes the home->pregrasp leg through the voxel A* planner (set `~pick_berry_use_astar:=false` to skip A* and drive straight to the pregrasp joints via a single `~move_arm_joints` target). The A* pre-path is planned by a berry-specific `_plan_astar_segments_berry` that runs WITHOUT any voxel obstacle input (`ignore_obstacles=True` -> `adapter.plan_joint_path_deg_no_obstacles`): the A* searches the bare reachability grid, does NOT consume the depth/obstacle voxels, and only WARNS (never raises) on an unreachable goal. The relaxed `~pick_berry_astar_max_cell_diff` (default 5 cells) is carried for parity but is unused in the no-obstacle mode. This is safe because the pregrasp is only a staging point and the exact grasp is reached afterward by the Cartesian leg. The berry pregrasp is its OWN straight-DOWN staging (NOT the bottle's fanned `pre_dist`/`delta_rz`): `_compute_grasp_and_pregrasp_berry` overrides the pregrasp position to directly below the berry at the same x,y by `~pick_berry_pregrasp_dz` (default 0.05 m), keeping the shared pregrasp orientation field, so the arm reaches under the berry then rises into it. The workspace gate is swapped to `_check_target_workspace_berry` (`check_target_workspace` override), which uses a lower floor `~pick_berry_workspace_min_z` (default `-0.2`, vs the grasp `~workspace_min_z`) because berries hang lower, AND a farther reach limit `~pick_berry_workspace_max_x` (default `0.42`, vs the grasp `~workspace_max_x` 0.39) because berries can sit farther out. After a successful grasp the handler runs `_retract_berry` (gated by `~pick_berry_retract`, default true): ONE pull-back waypoint then return to home joints. The waypoint depends on the grasp yaw rz: for **rz < 0** (where the make_retract_pose pull-back lands in an unreachable config) it goes to a fixed SIDE pose `(x=grasp x, y=±0.17 by arm [+0.17 left / −0.17 right], z=grasp z, rz=0)` keeping the berry wrist rx; for **rz ≥ 0** it uses `make_retract_pose(grasp_pose, grasp_pose, grasp_z, ~pick_berry_retract_x_target)` (default x target 0.15 m: slide back along the yaw to that x, y from rz, keeping z=tz and rx/rz). The waypoint is solved with the berry IK and driven via a single `~move_arm_joints`; then the arm is driven to its home joints (`_get_home_joints_rad(arm)` = `~{arm}_home_joints_deg`). A geometry skip still proceeds to home; a move failure returns `success=false` with "berry grasped but retract failed". `~pick_berry_dry_run` returns the chosen target + arm without motion. One berry per call by design; re-call to pick the next.
  * `~acquire_arm_control` / `~release_arm_control` (`std_srvs/Trigger`): SDK takeover / hand-back of the arms (see "Safety and Runtime Invariants"). `release_arm_control` is the only way the node gives the arms back while running; the orchestrator calls it once both arms are back at home (held object or not), and the handler itself refuses (`success=false`, control kept) when either arm measures more than `~release_arm_control_home_tolerance` rad (per-joint max abs, default 0.15) from `~{arm}_home_joints_deg` while `~release_arm_control_require_home` is true (skipped in simulation mode).
  * `~press_elevator_button` (`arm_grasp/PressElevatorButton`): two-leg press. A* to pre-press (button face shifted by `pre_press_dx` along `-x`), then a single direct waypoint to the press point. The hand point-gesture trigger fires in parallel (daemon thread) so the finger reshapes during the A* swing.
* Services consumed:
  * Hand triggers per side: `/g1_hand_{left,right}/{pre_grasp, grasp_5f, release, point_gesture}` (all `std_srvs/Trigger`). Missing sides do not crash the node; the grasp pipeline fails with a clear message and `GoHome` skips the missing side.
  * Berry hand triggers per side: `/g1_hand_{left,right}/pre_grasp_berry` (`~pre_grasp_berry_service_name_{right,left}`) and `/g1_hand_{left,right}/grasp_berry` (`~grasp_berry_service_name_{right,left}`), both `std_srvs/Trigger`. Used only by `~pick_berry` as its pre-grasp (berry approach pose) and post-grasp (berry pinch) hand legs — distinct from the bottle `pre_grasp`/`grasp_5f`. Both are implemented in `g1_hands` (`revo2_tactile_node.py`). `~pick_berry_dry_run:=true` skips them (detection + arm selection + planning only).
  * Camera object position: `/perception/get_object_position` (`g1_camera/GetObjectPosition`). Used only by `~grasp_bottle`.
  * Camera berry list: `/perception/get_berries` (`g1_camera/GetBerries`). Used only by `~pick_berry`; returns all berries (parallel arrays) in one call.

Conventions to keep:

* The `arm` field is `"left"` or `"right"` and selects ALL four arm-specific resources at once (NN model + scaler, voxel A* bitmap, pose-compensation offsets, hand clients). Do not add a request that mixes per-resource arm selection.
* The grasp `rz` rule (`atan2(y +/- 0.17, x)` with `+0.17` for right, `-0.17` for left), the elevator-button `rx` rule (`rx = +pi/2` for left, `rx = -pi/2` for right), and the berry-pick `rx` rule (`rx = +pi/2` for right, `rx = -pi/2` for left — note this is the opposite-arm sign of the elevator-button rule; bottle grasp keeps `rx = 0`) are baked into the training data distribution of the corresponding MLPs. Changing them requires re-training the models, not just editing the convention.
* The voxel A* path schema returned in `PlanGraspFromPoint.Response` packs waypoints as `N*5` flat float arrays (`pre_path_flat`, `target_path_flat`); downstream consumers MUST iterate in 5-tuples. Same packing applies to `PlanToPose.pre_path_flat`, `ExecuteAstarPathFromPoint.path_joint_angles_flat`, and `PressElevatorButton.{pre_path_flat, press_path_flat}`.
* `~lift_dz` is a pure-vertical lift (xy and orientation preserved, only z increases). Do not reintroduce the old `~lift_x` / `~lift_y` / `~lift_z` absolute target; the lift now follows the grasp pose.
* `~retract_after_grasp` / `~retract_x_target` produce a single retract joint target that the orchestrator can drive after lift (lift -> retract -> home). The IK is solved up front inside `_plan_grasp_from_target` so the orchestrator does not need to issue another IK request between waypoints.

## Voxel A* Backend

The backend lives under `src/arm_grasp/voxel_planner_deploy/` and is wrapped by `voxel_planner_adapter.VoxelPlannerAdapter`. It produces joint-space waypoint paths in the same schema `_plan_astar_segments` exposes to the rest of the node.

Preserve these invariants when refactoring:

* The backend expects obstacles in `torso_link` (x forward, y left, z up). The default extrinsics in the launch file and in the adapter mirror `g1_camera/config/params.yaml`; in this project's convention `g1_camera`'s `base_link` IS the URDF's `torso_link` (same physical frame, different label), so `~voxel_obstacle_frame_offset` stays at zero. Set non-zero only when the camera extrinsics start being measured from a different root frame.
* The planner grid is 4-deg/step on 5 joints with per-arm joint limits baked into the bitmap (see `voxel_planner_deploy/README.md` for the per-arm joint limits). Wrist_roll is NOT planned: the bitmap was sampled with `wrist_roll = 0` only. `voxel_planner_adapter._split_wrist_roll` peels the wrist_roll out of the IK goal before A*, plans the other four joints, then appends one trailing waypoint that rolls the wrist to its IK target value in place.
* `voxel_planner_adapter._check_goal_reachable` enforces a configurable tolerance between the A* final cell and the IK goal cell, defaulting to one cell (max axis diff <= 1, i.e. ~4 deg). If the soft-priority fallback lands further than that, `plan_joint_path_deg` raises `RuntimeError` so the executor refuses to drive the arm to a wrong-pose path. `plan_joint_path_deg` and the adapter-facing helper `_plan_astar_path_between_joints` both accept `max_cell_diff` (default 1) so callers whose final approach tolerates a coarser landing can relax the check per-call without affecting other call sites, and `task_label` (default `"Pregrasp"`) which prefixes the unreachable-goal error so operators can tell which goal failed; today `_handle_press_elevator_button` passes `max_cell_diff=3` (~12 deg) and `task_label="Prepress"` for the pre-press leg while grasp keeps the strict 1-cell default and the `"Pregrasp"` label. `plan_joint_path_deg_no_obstacles` (used only by `~debug_print_both_paths`) downgrades to a warning because it is diagnostic-only.
* The K-of-N persistence filter (`~voxel_obstacle_history_frames`, `~voxel_obstacle_history_min_obs`) is per arm. Default is `N=3, K=1`. Empty frames ARE appended to the deque so the rolling window stays time-correct; do not skip empty frames or stale entries will live forever.
* The 3x3 depth median filter (`~voxel_obstacle_depth_median_filter`) runs on the raw depth image BEFORE subsampling, to kill single-pixel speckle that would otherwise alias into a permanent obstacle voxel after stride. It falls back silently to raw depth if `scipy.ndimage` is not importable.
* Voxel inflation (`~voxel_obstacle_inflation_cells`) is 6-connected (face-neighbour) expansion, applied AFTER the K-of-N filter so transient noise voxels do not get amplified. The default is 0 because the planner bitmap was sampled from the URDF mesh.
* `~voxel_shortcut` (default `false` in the launch) governs whether the staged A* runs the 5D hyperrect compression on the returned path. The compression helper inside the backend (`compress_path_linecheck` in `voxel_phase4_astar.py`) samples the joint-space line with `np.rint`, which can declare a diagonal shortcut "clear" while the interpolated motion clips an obstacle voxel. Keep this off by default until the shortcut uses a conservative sweep check; the README's launch comment documents the failure mode.
* Each `latest_voxel_obstacles` call publishes the obstacle PointCloud2 (latched) when `publish=True`. The live-refresh timer (`~voxel_obstacles_live_rate`, default 5 Hz) ticks both arms' histories but publishes only `~voxel_obstacles_live_arm`'s voxel set so RViz does not flicker between two per-arm grids on the same topic.
* `_init_voxel_planner` does a one-time existence check for `voxel_config_bitmap_{left,right}.uint8` before constructing the adapter. If a bitmap is missing the node aborts at startup with a pointer to `decompress_once.py`; this is intentional and replaces lazy first-call surprises.

## ROS Home Writability

`_ensure_ros_home_writable` runs before `rospy.init_node`. If `~/.ros` is unwritable (read-only mount, container, root-owned cache directory) it switches `ROS_HOME` to `/tmp/ros_home` so rospy logging does not fail. Keep this in place; removing it makes the node abort under several common deployment configurations.

Per-arm berry-pick MLPs live at `models/grasp_berry/{left,right}/{best_model.pth, x_scaler.pkl}` (same architecture; used only by `~pick_berry`). The package `.gitignore` excludes the entire `models/` tree, so weights are NOT tracked in git.
* The 22 bottle / elevator-button / voxel files are pinned in `config/model_weights.yaml` to a specific commit of the private HF Hub repo `g1-intellect/g1-arm-abs-models`. `scripts/fetch_weights.py` downloads them on demand (idempotent: skips if on-disk sha256 already matches the manifest) and preserves HF's nested in-repo layout under `models/<filename>` (unlike `g1_camera`, which flattens). To make berry survive a clean provision, push these four files to HF Hub and add manifest entries (under `grasp_berry/{left,right}/`) the same way the bottle weights are pinned.
* `src/arm_grasp/weight_verify.py::verify_pinned_weights()` is called once from `arm_node_abs.__init__` (right after `rospy.init_node` and the logger setup, before any other parameter is read) and FATAL-exits the node on missing manifest, missing weight, or sha256 drift, with a hint to run `rosrun arm_grasp fetch_weights.py`. Manifest lookup is keyed by relative-to-models path because basenames repeat; do NOT switch this to basename lookup. Each manifest entry may carry `verify_sha256: false` to opt out of the sha256 check (existence-only); today the two ~14 GB `voxel_config_bitmap_{left,right}.uint8` files are the only opt-outs, because reading ~28 GB at every startup would add ~30 s of latency. Set `~force_full_weight_sha256:=true` to override every opt-out and verify all 22 entries.
* Updating a pinned weight: push the new file to HF Hub, then bump `hf_revision` and the matching `sha256` in `config/model_weights.yaml` in a single commit. Both `fetch_weights.py` (during build / setup) and `verify_pinned_weights()` (at node startup) consume the same manifest, so the operator only edits one place.
* Default `~{left,right}_model_path` and `~{left,right}_scaler_path` resolve relative to `models/grasp_bottle/` next to the package, computed from `os.path.dirname(os.path.abspath(__file__))` in `arm_node_abs.py`. Default `~{left,right}_berry_model_path` / `~{left,right}_berry_scaler_path` resolve the same way relative to `models/grasp_berry/` (loaded in `params.load_params`). The elevator-button paths come from `elevator_button_ik.ELEVATOR_BUTTON_MODELS_ROOT`, computed the same way from `os.path.dirname(os.path.dirname(_THIS_DIR))`. Both schemes work whether the package is imported through the source tree or through the `catkin_ws/src/arm_grasp` symlink.
* `_select_torch_device` (in both `solve_grasp_pose.py` and `elevator_button_ik.py`) probes CUDA with a tiny op before declaring it usable. `torch.cuda.is_available()` returns true for GPUs whose compute capability the installed wheel cannot run on (e.g. RTX 5070 sm_120 on a cu118 build), so the probe is what gates the actual fallback to CPU. Keep this; bypassing it surfaces as a silent CUDA kernel-launch failure under the first IK call.

## Safety and Runtime Invariants

Do not loosen these without explicit user approval:

* The `ArmController._ctrl_motor_state` loop runs in a daemon thread at `~control_frequency` (default 250 Hz) and uses `clip_arm_q_target` to bound the per-cycle joint delta to `velocity_limit * control_dt`. New motion entry points MUST go through `ctrl_dual_arm` / `ctrl_left_arm` / `ctrl_right_arm` so they pick up this clip; writing to `_msg.motor_cmd[*]` directly is unsafe.
* `~simulation_mode:=true` is the only path that skips DDS bring-up. In simulation mode the controller fakes a zero-state `LowState` and never opens a `ChannelPublisher` / `ChannelSubscriber`. Tests and dry runs MUST use this gate; reaching the SDK with a missing `G1_NETWORK_INTERFACE` raises `RuntimeError` from `ArmController.__init__`.
* `ArmController.start(connect_retries, connect_retry_interval, state_timeout)` retries the robot connection (DDS bring-up + first-`rt/lowstate` handshake, default `state_timeout=10 s`) up to `connect_retries` times with `connect_retry_interval` between attempts, because the link is flaky right after power-on / while the interface settles. `arm_node_abs.py` wires this from `~connect_retries` (default 3) and `~connect_retry_interval` (default 2.0 s); only `start()` returning `False` after all attempts aborts the node. The retry re-runs `_init_sdk` ONLY if `_lowcmd_publisher` is still `None` (a partial bring-up): `ChannelFactoryInitialize` creates a process-global participant, so re-initializing a live channel set would leak it — once channels exist, only the state handshake (and a re-spawned subscribe thread) is retried. `simulation_mode` short-circuits before the retry loop.
* Motion-mode (`~motion_mode:=true`, default) routes commands through `rt/arm_sdk` gated by the weight channel (`motor_cmd[WEIGHT_INDEX].q`, 0 = robot's own arm controller, 1 = this SDK). The controller STARTS RELEASED (weight 0) so the G1 keeps its native arm swing; `ArmController.acquire_control()` seeds `_q_target` with the measured arm pose and ramps 0->1, `release_control()` ramps 1->0, both over `~control_switch_delay` seconds (default 0.5 s, step interval 0.02 s) followed by a `~control_switch_settle` hold (default 0.5 s) before returning, and both blocking + idempotent under `_switch_lock`. `ArmControllerProxy` round-trips the same two ops to the child and mirrors `has_control`. Every motion service handler in `arm_node_abs.py` calls `_ensure_arm_control()` before moving (auto-takeover; plan-only services such as `plan_grasp_from_point` / `plan_to_pose` / `infer_grasp_from_point` and `pick_berry` dry runs do not); the node never releases on its own except after the startup home move (`~release_arm_control_after_init_home`, default true) and on `~release_arm_control`, which additionally refuses unless both arms measure within `~release_arm_control_home_tolerance` of their home joints (`~release_arm_control_require_home`; `_arms_at_home_error` in `arm_node_abs.py`), so a bookkeeping gap in the orchestrator can never hand an extended arm to the robot's own arm swing (the check is pose-only; a held object does not block it). `main_process` is the owner of the hand-back decision: it releases at the first safe point after an arm task or before a walking leg, but only when no arm is away from home (a grasped object carried at home is handed back too), so an extended arm stays under SDK control until go_home / release has homed it. `ctrl_*` calls without control log one warning and are otherwise ignored by the robot (weight 0). `stop(release_control=True)` is the supported exit path; bypassing the ramp jolts the arm.
* `~clip_inferred_joints_to_limits` (default `true`) clamps NN-inferred joints into `ARM_JOINT_LIMITS` (`joint_index.py`) before issuing motion. The MLPs can drift outside the URDF limits near workspace edges; without the clamp the controller would attempt unreachable configurations.
* `~workspace_max_x` (default 0.39) and `~workspace_min_z` (default `-0.02`) gate the grasp pipeline's accepted target xyz. The voxel A* grid bounds (`[0, 0.6] x [-0.7, 0.7] x [-0.4, 0.4]` in `torso_link`) are wider, so the workspace clamp is the policy-level limit; raising it requires verifying both the NN training distribution and the planner workspace overlap. The press pipeline (`_handle_press_elevator_button`) gates ALL four of its waypoints (press, pre_press, mid_press, retract) against the SEPARATE `~press_elevator_button_workspace_max_x` / `~press_elevator_button_workspace_min_z` (passed into `_check_target_workspace` as the `max_x` / `min_z` overrides), not the grasp pair, because the press fingertip reaches farther forward than the grasp palm. Both press params default to the grasp values so press behaviour is unchanged until set; the launch raises `press_elevator_button_workspace_max_x` above the grasp 0.39 default. Keep the press max_x at or below the voxel A* grid edge (`x <= 0.6`, `z >= -0.4` in `torso_link`) or the planner cannot represent the goal cell, and the same NN-training-distribution caveat applies to the elevator-button MLP. The berry pick (`_handle_pick_berry`) similarly gates its target against SEPARATE berry bounds via `_check_target_workspace_berry`: a lower floor `~pick_berry_workspace_min_z` (default `-0.2`) because berries hang lower, and a farther reach `~pick_berry_workspace_max_x` (default `0.42`, vs the grasp 0.39) because berries can sit farther out; keep min_z at or above the voxel A* grid floor (`z >= -0.4`), max_x at or below the grid edge (`x <= 0.6`), and both within the berry MLP's training distribution.
* The grasp pipeline calls `/g1_hand_{arm}/pre_grasp` before motion to pregrasp, then `/g1_hand_{arm}/grasp_5f` after motion to grasp. `~grasp_5f_retries` (default 3) and `~grasp_retry_interval` (default 0.4 s) bound how many times the grasp close is reattempted on hand-side failure. If the hand service is missing entirely, the pipeline aborts with a clear message; missing sides do NOT crash the node.
* `GoHome` (`std_srvs/Trigger`) releases BOTH hands and homes BOTH arms; the per-arm `GoHomeArm` releases the targeted side only. The release dispatch can fire in a background thread when `~release_non_blocking_on_home:=true` (default) so the arm starts homing without waiting on the fingers; that parallelism only saves ~2 s but the trade-off is silently swallowing release errors. Set `~release_non_blocking_on_home:=false` if synchronous error reporting matters.
* Press-elevator-button posts the hand `point_gesture` trigger in a daemon thread `~press_elevator_button_hand_settle_sec` seconds into the A* swing so the finger reshapes during motion. Removing the daemon delay either races the gesture against the arm (hand starts moving before the arm has cleared body) or starts the gesture only after the arm reaches pre-press (~1 s slower per call).

## Known State Drift

Surface these to the user rather than silently fixing; they may carry hidden intent.

* `msg/ArmState.msg`, `msg/EndEffectorPose.msg`, and `msg/IKResult.msg` are tracked in git but are NOT in `CMakeLists.txt::add_message_files` and are not imported anywhere. Either they are placeholders for a future ROS-topic publisher (the `ArmState` comment says "Published at 50 Hz on `~arm_state`", which does not exist) or they are leftover from an earlier design. Ask before either wiring them up or deleting them.
* `README.md` documents a smaller parameter surface than what `arm_node_abs.py` actually reads. Examples not yet in the README: `~press_elevator_button_*`, `~point_gesture_service_name_*`, `~plan_to_pose` (and the matching service section), `~clip_inferred_joints_to_limits`, `~workspace_max_x` / `~workspace_min_z`, `~voxel_obstacle_history_frames` / `~voxel_obstacle_history_min_obs`, `~voxel_obstacle_inflation_cells`, `~voxel_obstacle_depth_median_filter`, `~voxel_obstacles_live_rate` / `~voxel_obstacles_live_arm`, `~release_non_blocking_on_home`, `~enable_pregrasp_breakpoint`, `~pre_to_target_waypoint_count`, `~debug_print_both_paths`, `~connect_retries` / `~connect_retry_interval`. README must be updated alongside any new parameter or behaviour change; do not assume the existing README is authoritative when deriving defaults.
* `arm_controller.py::_ensure_local_unitree_sdk_path` walks five `..` from the source file. As called out in the conda-environment section, that path-walk reaches the repo root only when the file is imported through the `catkin_ws/src/arm_grasp` symlink. The supported configuration always installs `unitree_sdk2py` into `g1_intellect_env`, so the fallback is a safety net rather than a primary path. Surface the brittleness to the user before changing the depth or replacing it with a `realpath` walk.

## Build and Catkin Notes

* This is a Python-only catkin package. `CMakeLists.txt` declares:
  * `find_package(catkin REQUIRED COMPONENTS g1_camera rospy std_msgs std_srvs message_generation)`.
  * `catkin_python_setup()` to expose `src/arm_grasp/` (`setup.py` maps `arm_grasp` to `src/arm_grasp`).
  * `add_service_files(FILES MoveArmJoints.srv InferGraspFromPoint.srv ExecuteGraspFromPoint.srv ExecuteAstarPathFromPoint.srv PlanGraspFromPoint.srv PlanToPose.srv GoHomeArm.srv PressElevatorButton.srv)`.
  * `generate_messages(DEPENDENCIES std_msgs)`.
  * `catkin_package(CATKIN_DEPENDS g1_camera rospy std_msgs std_srvs message_runtime)`.
  * `catkin_install_python(PROGRAMS scripts/arm_node_abs.py scripts/fetch_weights.py DESTINATION ${CATKIN_PACKAGE_BIN_DESTINATION})`. `scripts/dump_voxel_obstacles.py` is NOT in this list today; it is invoked directly via `rosrun` because the package directory is exposed on the path. Add it explicitly if it ever needs to be installed.
* Adding a new ROS-facing Python entry point requires editing the `catkin_install_python` block, adding a shebang plus executable bit to the new file, and (if the entry point introduces a new `.msg` or `.srv`) updating `add_message_files` / `add_service_files`, `generate_messages(DEPENDENCIES ...)`, and `package.xml` (`build_depend` + `exec_depend`).
* Resource paths inside launch files MUST go through `$(find arm_grasp)/...`. Do not hardcode absolute paths. The default RViz config is `$(find arm_grasp)/config/voxel_obstacles.rviz`.
* The package contains a `models/abstraction_map/` directory with ~28 GB of decompressed bitmaps after `decompress_once.py` runs. The package `.gitignore` excludes the entire `models/` tree (MLP weights and voxel bitmaps alike); none of it ships in git.

## External Dependencies

* ROS Noetic (`rospy`, `std_msgs`, `std_srvs`, `sensor_msgs`, `tf2_ros`, `message_runtime`, `rviz`) from the system install. The package consumes `g1_camera/GetObjectPosition` for the legacy `grasp_bottle` path; that dependency is declared in both `CMakeLists.txt` and `package.xml`.
* `unitree_sdk2py` (Unitree G1 DDS Python SDK). Install with `pip install -e <repo>/external/unitree_sdk2_python` inside `g1_intellect_env`. Also requires `cyclonedds==0.10.2`, which is workspace-pinned. `arm_controller.py::_init_sdk` surfaces a precise install hint when the SDK or `cyclonedds` is missing.
* `torch==2.4.1+cu118`, `numpy==2.2.6`, `scikit-learn==1.7.2` (brings `joblib`) for the MLP IK paths. Both `solve_grasp_pose.py` and `elevator_button_ik.py` probe CUDA before using it.
* `numba>=0.61` (pinned in the top-level `requirements.txt`, accepts `numpy 2.2.6`) for the voxel A* kernels. Required by `voxel_numba_kernels.py`; llvmlite is pulled in transitively.
* `scipy.ndimage` is optional. When absent, `VoxelPlannerAdapter` skips the 3x3 depth median pre-filter and logs a one-time warning.
* `huggingface_hub` (pinned at the workspace level in `requirements.txt`, `>=1.0,<2.0`) is consumed by `scripts/fetch_weights.py` (downloader) and indirectly by `arm_node_abs.py` via the manifest read inside `weight_verify.verify_pinned_weights()` at startup. The HF Hub repo `g1-intellect/g1-arm-abs-models` is private, so each deployment machine needs a fine-grained read token either persisted via `hf auth login` (stored at `~/.cache/huggingface/token`) or injected via the `HF_TOKEN` environment variable. `fetch_weights.py` reads the token via the standard fallback chain (`HF_TOKEN` env or cached token file).

## Integration With the Rest of the Workspace

* Upstream:
  * `g1_camera` provides `/camera/aligned_depth_to_color/image_raw` + `/camera/color/camera_info` (consumed by the voxel A* adapter), `/perception/get_object_position` (consumed by `~grasp_bottle`), and `/perception/get_berries` (consumed by `~pick_berry`). The extrinsic defaults in `arm_node_abs.launch` and in `arm_node_abs.py` MUST match `g1_camera/config/params.yaml`; if those values shift, mirror them in the same change set.
  * `g1_hands` provides per-side hand Trigger services (`/g1_hand_{left,right}/{pre_grasp, grasp_5f, release, point_gesture}`). Renaming any of those topics requires updating both `g1_hands/CLAUDE.md` and the per-side `~{pre_grasp,grasp_5f,release,point_gesture}_service_name_*` defaults here in the same change set.
  * `g1_slam` (when running) owns the canonical TF chain `base_link -> ... -> torso_link -> ... -> camera_color_optical_frame`. Launch this package with `publish_tf_stubs:=false` whenever `g1_slam/launch/transforms.launch` is up.
* Downstream:
  * `main_process` (or any future orchestrator) consumes `~plan_grasp_from_point`, `~plan_to_pose`, `~move_arm_joints`, the per-arm hand services, and the JSON / camera lookups in its own composition logic. The contract is the service surface documented above plus the flat-`N*5`-floats waypoint packing; renaming or restructuring any service requires a coordinated edit in the consumer.
  * No direct interaction with `g1_navigation`, `g1_locomotion`, `g1_perception`, `g1_gimbal`, or `g1_slam` at the topic / service level today.
